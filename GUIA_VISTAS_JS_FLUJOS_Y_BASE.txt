======================================================================
1.1 ACLARACION IMPORTANTE SOBRE MODALES, CONTROLLERS Y SQL
======================================================================
Si estabas buscando las cargas o inserciones directamente en los modales o
en los controller, ahi no las vas a ver.

Regla real del proyecto:

- el modal solo captura datos en la vista
- funcionalidad_global.js toma esos datos y llama a la API
- server.js recibe la ruta
- el controller solo delega
- el model es donde vive el SQL real
- db.js es donde esta la conexion y la transaccion

En otras palabras:

- los modales NO consultan PostgreSQL
- los controller NO escriben SQL
- los model SI hacen SELECT, INSERT, UPDATE y DELETE
- db.js SI crea la conexion con new Pool(config.database)

Ejemplos concretos:

Conexion a la base:
- backend/db.js:4 -> const pool = new Pool(config.database);
- backend/db.js:8 -> query(text, params)
- backend/db.js:15 -> withTransaction(callback)

Configuracion de la base:
- backend/env.js:57 -> connectionString: mergedEnv.DATABASE_URL
- backend/env.js:60 -> host: mergedEnv.PGHOST || "127.0.0.1"

Ejemplo de insercion real:
- backend/models/auth.model.js:254 -> INSERT INTO usuarios
- backend/models/auth.model.js:284 -> INSERT INTO usuarios_credenciales
- backend/models/auth.model.js:298 -> INSERT INTO cuentas

Ejemplo de lectura real:
- backend/models/profile.model.js:162 -> FROM usuarios
- backend/models/transfer.model.js:174 -> FROM cuentas
- backend/models/base.model.js:1027 -> FROM transacciones

Ejemplo de actualizacion real:
- backend/models/profile.model.js:208 -> UPDATE usuarios
- backend/models/transfer.model.js:266 -> UPDATE cuentas
- backend/models/alerts.model.js:24 -> UPDATE alertas_usuario

Ejemplo de borrado real:
- backend/models/alerts.model.js:44 -> DELETE FROM alertas_usuario


======================================================================
2. ESTRUCTURA GENERAL DEL FRONTEND
======================================================================
Todas las vistas usan un solo archivo JS principal:

- recursos/scripts/funcionalidad_global.js

Ese archivo detecta la pagina actual y decide que inicializador correr con:

- linea 67: iniciar_aplicacion()
- linea 115: obtener_pagina_actual()

La seleccion por pagina se hace asi:

- login.html -> inicializar_login()
- principal.html -> inicializar_principal()
- perfil.html -> inicializar_perfil()
- operaciones.html -> inicializar_transferencias()
- movimientos.html -> inicializar_movimientos()
- mercado_forex.html -> inicializar_portal_forex()
- aprendizaje_forex.html -> inicializar_portal_forex()
- cuestionario_forex.html -> inicializar_portal_forex()
- simulador_inversion.html -> inicializar_simulador()

Librerias usadas en frontend:

- SweetAlert2 para confirmaciones y toasts
- Chart.js para graficos de movimientos, forex y simulador

SweetAlert2 se carga desde las vistas HTML por CDN, por ejemplo:

- views/login.html
- views/principal.html
- views/perfil.html
- views/operaciones.html
- views/movimientos.html
- views/mercado_forex.html
- views/aprendizaje_forex.html
- views/cuestionario_forex.html
- views/simulador_inversion.html

Y se ejecuta en el JS principal principalmente desde:

- mostrar_toast_lateral() -> toast lateral
- confirmar_accion() -> modal de confirmacion

Importante:
- SweetAlert2 no consulta la base
- SweetAlert2 no hace SQL
- SweetAlert2 solo muestra UI y devuelve la respuesta del usuario

======================================================================
Punto unico de salida hacia backend:

- recursos/scripts/funcionalidad_global.js
- linea 358: consumir_api(ruta, opciones)

Esta funcion:

- arma fetch()
- agrega Authorization: Bearer <token> si existe
- manda body en JSON
- recibe JSON
- si hay error HTTP, lo transforma en Error legible

Esto significa que toda la captura de datos desde formularios HTML termina
pasando por consumir_api().

======================================================================
9. DONDE SE EXTRAEN LOS DATOS Y DONDE SE ESCRIBEN EN BASE
======================================================================

Antes de los casos concretos, este es el recorrido exacto:

1. El usuario llena un formulario en una vista HTML.
2. El submit lo maneja recursos/scripts/funcionalidad_global.js.
3. Ese JS llama a consumir_api() en la linea 358.
4. consumir_api() manda fetch() a una ruta /api/...
5. server.js recibe la ruta y el body.
6. server.js usa parseJsonBody() para extraer el JSON.
7. server.js llama al controller correcto.
8. El controller delega al model correcto.
9. El model ejecuta SQL real con query() o withTransaction().
10. db.js usa el pool de PostgreSQL y ahi ocurre la carga o insercion real.

Resumen corto:

HTML -> funcionalidad_global.js -> server.js -> controller -> model -> db.js -> PostgreSQL

Puntos tecnicos clave:

- Extraccion del body JSON:
  - server.js:114 -> parseJsonBody()

- Conexion compartida a PostgreSQL:
  - backend/db.js:4 -> const pool = new Pool(config.database)

- Consulta simple:
  - backend/db.js:8 -> query(text, params)

- Escritura transaccional:
  - backend/db.js:15 -> withTransaction(callback)

======================================================================
13. COMO LEVANTAR UN TUNEL PUBLICO
======================================================================

Esto sirve cuando un correo necesita abrir un enlace real y no localhost.

13.1 Levantar backend primero
Comando:
node server.js

13.2 Crear tunel rapido con cloudflared
Comando:
cloudflared tunnel --url http://127.0.0.1:3000

13.3 Tomar la URL publica generada
Ejemplo:
https://tu-subdominio.trycloudflare.com

13.4 Colocarla en .env
Variable:
APP_BASE_URL=https://tu-subdominio.trycloudflare.com

13.5 Reiniciar backend
Hay que reiniciar node server.js para que backend/env.js vuelva a leer la
nueva APP_BASE_URL.

13.6 Resultado
Desde ese momento los correos que se generen usaran la URL publica y ya no
apuntaran a localhost.

Nota importante:
- los quick tunnels de Cloudflare cambian si los reinicias
- si cambia la URL, vuelve a actualizar APP_BASE_URL y reinicia el backend

14. RESUMEN RAPIDO DEL RECORRIDO COMPLETO
======================================================================

HTML -> funcionalidad_global.js -> consumir_api() -> server.js ->
controller -> model -> db.js -> PostgreSQL -> response JSON ->
funcionalidad_global.js -> renderizado en la vista.

Si quieres ubicar exactamente donde nace un flujo:

- formulario en HTML
- submit dentro de funcionalidad_global.js
- endpoint en server.js
- controller relacionado
- model relacionado
- query SQL dentro del model
